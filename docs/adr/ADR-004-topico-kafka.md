# ADR-004: tópico Kafka de resultados

- **Status:** Aceito
- **Contexto:** Além da fila de trabalho RabbitMQ, o projeto precisa publicar o resultado da análise e permitir acompanhar o estado da transação sem compartilhar bancos entre serviços.
- **Decisão:** RabbitMQ permanece como canal de entrada para o trabalho de análise. Depois do commit de uma nova análise, `analysis-service` publica um evento `AnalysisCompleted` no tópico `analysis.completed`, usando o ID da transação como chave. `transaction-service` consome o tópico com seu próprio grupo e atualiza o estado e resultado no banco que possui. O tópico tem uma partição e uma réplica no ambiente local.
- **Alternativas consideradas:** Substituir RabbitMQ por Kafka; publicar a mesma transação nos dois brokers e consumir ambos; não adicionar um fluxo de eventos de resultados.
- **Justificativa:** Cada tecnologia tem um papel distinto: RabbitMQ distribui trabalho de análise; Kafka transporta o resultado para acompanhamento e para consumidores independentes. Publicar apenas quando uma nova linha é inserida também evita emitir outro evento quando a mensagem de entrada é repetida.
- **Consequências:** A atualização de status no Serviço de Transações é eventual. O tratamento do evento é idempotente por transação, mas o consumo do Kafka e a gravação no PostgreSQL não são atômicos. Publicar após o commit evita anunciar uma análise que não foi persistida, mas uma falha entre o commit e a publicação ainda pode deixar o evento faltando. O padrão Outbox é uma evolução futura. O broker local de nó único não oferece alta disponibilidade.
